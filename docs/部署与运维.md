# Relay / Unity 自动化调度台：部署与运维

本文档对应当前实现：网页负责发起任务、追加微调轮次、查看队列和控制工位；本地 Node 控制服务负责 SQLite 持久化、调度、Hyper-V、来宾 Git、宿主机 Codex 和 Unity Skill 协调。

> **当前只运行真实宿主机集成。** 生产 Mock 已移除。服务启动时会检查 Hyper-V 管理权限、真实 VM 清单、Codex CLI 版本与登录状态；检查失败时调度器保持暂停。

## 1. 运行结构

```text
浏览器 :3000
   │ HTTP + SSE
   ▼
Relay 控制服务 :4317 ── SQLite / 附件 / JSONL 日志
   ├─ Hyper-V PowerShell（固定白名单脚本）
   ├─ PowerShell Direct ── 子机内 Git
   ├─ SMB 路径 ── 宿主机 Codex 读写项目
   └─ Codex CLI ── Unity Skill（子机完整 Unity GUI）
```

核心对象不是“一次性任务”，而是三层关系：

- **Task**：长期存在的一条工作线，绑定一个项目、一条远程 Git 分支和一个 Codex `thread_id`。
- **Turn**：Task 中的一次需求或微调；排队单位是 Turn。没有空闲工位时，Turn 保留在队列中等待。
- **Worker**：Hyper-V 子机工位。检查点功能启用后每一轮从 `PROJECT_READY` 恢复；准备检查点期间可关闭恢复功能。

第一次 Turn 默认创建 `codex/task-0001-<标题>` 形式的分支。成功后保存远程 commit SHA 和 Codex `thread_id`。同一 Task 在排队、执行、失败现场保留或关闭状态都能继续接收消息；调度器始终按 Turn 顺序执行。正常交付后的后续 Turn 会在兼容工位上拉取同一远程分支并恢复相同 `thread_id`；失败现场上的下一轮固定回到原工位，跳过检查点还原和 Git 重置后恢复对话。

## 2. 宿主机快速启动

### 2.1 前置条件

- Windows 10/11 或 Windows Server，已启用 Hyper-V。
- Node.js `>= 22.13.0`。
- Codex CLI 已安装并由运行 Relay 的同一账户完成登录。
- 当前账户能执行 `Get-VM`。
- 在项目根目录运行命令。

### 2.2 启动

```powershell
npm install
Copy-Item .env.example .env.local
# 编辑 .env.local 后启动
npm run dev
```

打开 `http://localhost:3000`。控制服务默认位于 `http://127.0.0.1:4317`。如果两个进程分开启动，可使用：

```powershell
npm run dev:web
node .\server\index.mjs
```

控制服务不会创建示例数据。首次进入网页后配置真实 Project 与 Worker。`GET /api/runtime` 会返回 Hyper-V 权限、真实 VM 清单以及 Codex CLI 状态；它不会返回任何 Codex 凭据。

若旧数据目录中仍有早期示例记录，Relay 不会自动删除它们。确认没有需要保留的任务历史后，可在网页中逐项删除，或停服备份后换用新的 `PIPELINE_DATA_DIR`。

## 3. Hyper-V 宿主机前置

### 3.1 宿主机账户与软件

建议创建一个专用 Windows 服务账户，例如 `relay-svc`。下列操作必须始终使用这个同一账户：

1. 运行 Relay 控制服务；
2. 执行 Codex CLI 登录；
3. 创建 DPAPI `PSCredential` 文件；
4. 访问工位 SMB 共享；
5. 读取 `CODEX_HOME` 和 `PIPELINE_DATA_DIR`。

该账户需要：

- Hyper-V Administrators 成员资格；初次配置和排障时使用提升的 PowerShell。
- 对每个 SMB 项目共享具有修改权限。
- 对 `C:\ProgramData\Relay\data`、`secrets` 和 `codex-home` 具有读写权限。
- Node.js `>= 22.13.0`、Codex CLI 和 Git 可用。

管理员 PowerShell 中先检查：

```powershell
.\scripts\hyperv\Test-PipelineHost.ps1
```

应看到 `hyperVModule`、`nodeFound`、`codexFound`、`elevated` 均为 `true`。若服务使用绝对路径，可通过 `.env` 的 `PIPELINE_CODEX_COMMAND` 和 `PIPELINE_POWERSHELL_COMMAND` 指定。

### 3.2 内部交换机

用 Hyper-V 管理器创建一个**内部**虚拟交换机，例如 `Relay-Internal`：

1. Hyper-V 管理器 → 右侧“虚拟交换机管理器”；
2. “新建虚拟网络交换机” → “内部” → 创建；
3. 在宿主机“网络连接”中找到对应 `vEthernet (Relay-Internal)`；
4. 手动设置宿主机 IPv4，例如 `172.30.240.1 / 255.255.255.0`，内部网卡不填网关；
5. 每台子机增加/连接一张该交换机网卡，依次使用 `172.30.240.11`、`.12` 等固定地址。

内部网段只负责宿主机到子机的稳定管理流量。子机需要访问 Git 远端、许可证或公司资源时，可另保留公司有线网对应的外部交换机网卡。不要在内部网卡上设置与公司网冲突的默认网关。

若公司其他设备需要直接访问子机 Unity Skill，应优先让该服务监听子机公司网卡，并由公司防火墙精确开放所需端口。不要把整个内部管理网段无条件暴露到公司 LAN。

### 3.3 Hyper-V 集成服务

对每台工位执行：Hyper-V 管理器 → 右键虚拟机 → “设置” → “管理” → “集成服务”，勾选：

- **检测信号（Heartbeat）**：当前健康检查会读取它；
- **时间同步（Time Synchronization）**：保证 Git、事件和 Codex 日志时间一致；
- **来宾服务接口（Guest Service Interface）**：便于后续宿主机/来宾文件服务和运维工具。

也可在管理员 PowerShell 中确认：

```powershell
Get-VMIntegrationService -VMName 'lin-worker-01' |
  Format-Table Name, Enabled, PrimaryStatusDescription
```

Relay 当前通过 **PowerShell Direct** 执行来宾 Git，所以不依赖子机 WinRM 或 SSH，也不要求管理网段在 PowerShell Direct 执行时可用；但健康检查、SMB 和 Unity Skill 仍依赖相应服务与网络。

### 3.4 子机 Windows 与 Unity

每个工位需要完整 Windows 和完整 Unity GUI，不使用无头模式：

- 不挂载 GPU-P/DDA；工位只承载编辑器与 Unity Skill，不运行游戏。这样也避免设备直通限制检查点恢复。
- 为 Unity 导入和编译预留足够的固定/保底内存与 CPU，避免多工位同时启动时宿主机换页。
- 关闭睡眠、休眠和自动锁屏；电源计划保持运行。
- 用组织更新策略禁止工位在可调度时段自动重启；系统更新只在基线维护窗口完成并重新做 canary，不建议永久放弃安全更新。
- 配置自动登录到专用本地账户，使 Unity GUI 和 Unity Skill 能在还原后自动运行。
- 安装项目要求的 Unity/Hub、Git、LFS 和依赖工具。
- 在子机内设置 Git `user.name`、`user.email`，并完成远端 SSH key 或 Credential Manager 登录。
- 项目位于固定来宾路径，例如 `D:\Work\unity-client`。
- Unity 打开该项目，等待首次导入、脚本编译和 Domain Reload 完成。
- Unity Skill 随 Unity 启动，并监听可从宿主机访问的固定 URL。
- 在子机管理员 PowerShell 中运行 `guest-tools\\unity-dialog-guard\\Install-UnityDialogGuard.ps1`。它以交互式登录任务常驻子机桌面，按白名单处理 Unity 阻塞弹窗，并把首次人工处理的新弹窗学习到可复制的 `learned-rules.json`。详细规则与同步方式见该目录的 README。
- Unity Skill 必须提供“保存全部资产”的 HTTP 操作。当前 `Save-UnityProject.ps1` 会向 `unitySaveUrl` POST：

```json
{ "action": "saveAll", "waitForCompletion": true }
```

只有返回 2xx 才允许继续 commit/push 和释放工位。真实模式默认不允许跳过该步骤。

### 3.5 SMB 项目共享

共享项目磁盘或项目目录，例如把 `D:\Work` 共享为 `Work`，宿主机最终应能访问：

```text
\\172.30.240.11\Work\unity-client
```

建议：

- 共享权限和 NTFS 权限均只授予服务账户所需的“读取/更改”，不要开放 Everyone 完全控制。
- 在宿主机使用服务账户实际执行 `Test-Path '\\172.30.240.11\Work\unity-client'`。
- 若 SMB 使用子机本地账户，使用 Windows 凭据管理器预先保存凭据；不要把 SMB 明文密码写入 Relay 数据库或 `.env`。
- Codex 由宿主机启动，并直接以该 UNC 路径作为工作目录；Git 命令则由 PowerShell Direct 在子机本地磁盘上执行，避免宿主机在 SMB 上运行 Git。

### 3.6 `PROJECT_READY` 检查点

建立检查点前应满足：

- 当前是项目默认基线分支，工作区无未提交更改；
- Git 远端凭据有效；
- Unity 已打开正确项目且编译/导入完成；
- Unity Skill 健康地址和保存地址可用；
- `\Relay\UnityDialogGuard` 计划任务正在运行，已知 Reload 测试弹窗能被自动处理；
- SMB 从宿主机可访问；
- 自动登录、禁用睡眠等系统设置已完成。

若目标是恢复后立即得到已运行的 Unity GUI，使用能保存运行状态的**标准检查点**。检查点名称必须精确为 `PROJECT_READY`，或在项目/工位配置中填写实际名称。不要手动移动、改名或合并 `.avhdx` 文件；检查点合并和删除只通过 Hyper-V 管理器或受控 PowerShell 完成。

### 3.7 DPAPI `PSCredential`

该文件只用于宿主机通过 PowerShell Direct 登录子机，不是 Git、SMB 或 Codex 的通用凭据。

使用**将来运行 Relay 服务的同一 Windows 账户**执行：

```powershell
New-Item -ItemType Directory -Path 'C:\ProgramData\Relay\secrets' -Force
.\scripts\hyperv\Initialize-PipelineCredential.ps1 `
  -Destination 'C:\ProgramData\Relay\secrets\lin-worker-01.xml' `
  -UserName 'lin-worker-01\lin-worker-1'
```

输入子机本地账户密码。生成文件受 Windows DPAPI 保护，只能由创建它的 Windows 账户在同一台宿主机解密。限制该目录 ACL；不要提交、复制到其他宿主机或放进共享目录。若更换服务账户、宿主机或子机密码，必须重新生成。

## 4. Codex CLI 与持久会话

### 4.1 登录和 `CODEX_HOME`

在服务账户的交互式会话中设置持久目录并登录：

```powershell
New-Item -ItemType Directory -Path 'C:\ProgramData\Relay\codex-home' -Force
$env:CODEX_HOME = 'C:\ProgramData\Relay\codex-home'
codex login
codex --version
```

如果登录方式要求浏览器，先用该账户完成一次交互登录。Windows 服务启动时必须继承相同 `CODEX_HOME`，否则会表现为“交互终端可用、服务内未登录”。不得把 Codex token 放进网页项目配置。

每个 Task 第一次执行时，Relay 使用 `codex exec --json`，捕获 `thread.started` 中的 `thread_id` 并写入 SQLite。后续 Turn 使用同一 ID 执行 `codex exec resume <thread_id> <需求>`。Relay 不使用 `--ephemeral`，因此对话索引也会留在 `CODEX_HOME`。

持久性有两层，缺一不可：

1. SQLite 中的 Task → `thread_id`、分支、Turn 历史；
2. `CODEX_HOME` 中的 Codex 会话状态。

备份时应同时覆盖 `PIPELINE_DATA_DIR` 和 `CODEX_HOME`。复制 SQLite 前停止 Relay，或使用 SQLite 在线备份工具；不要只复制 `pipeline.sqlite` 而遗漏 `-wal` 文件。

## 5. 真实模式环境变量和网络访问

复制 `.env.example` 为宿主机私有配置，例如 `C:\ProgramData\Relay\relay.env`，至少修改：

```dotenv
PIPELINE_ADAPTER=hyperv
PIPELINE_HOST=0.0.0.0
PIPELINE_PORT=4317
PIPELINE_ALLOWED_ORIGINS=http://10.100.3.175:3000
PIPELINE_DATA_DIR=C:\ProgramData\Relay\data
CODEX_HOME=C:\ProgramData\Relay\codex-home
PIPELINE_CODEX_MODEL=gpt-5.6-sol
PIPELINE_CODEX_REASONING_EFFORT=xhigh
PIPELINE_CODEX_SERVICE_TIER=default
PIPELINE_CODEX_TIMEOUT_MINUTES=90
PIPELINE_GIT_AUTHOR_NAME=Relay Unity Orchestrator
PIPELINE_GIT_AUTHOR_EMAIL=relay-unity-orchestrator@localhost
PIPELINE_CHECKPOINTS_ENABLED=false
PIPELINE_ALLOW_UNITY_SAVE_SKIP=false
```

启动控制服务：

```powershell
node --env-file='C:\ProgramData\Relay\relay.env' .\server\index.mjs
```

Relay 不再要求单独的 API 访问令牌。网页首次进入时只填写使用者名称，该名称用于任务、消息和人工操作的归属记录，不是权限校验。监听 `0.0.0.0` 只表示接受其他网卡连接，因此仍必须：

`PIPELINE_CODEX_MODEL`、`PIPELINE_CODEX_REASONING_EFFORT` 和 `PIPELINE_CODEX_SERVICE_TIER` 是未显式提交任务配置时的服务端回退值，默认分别为 `gpt-5.6-sol`、`xhigh` 和 `default`。网页“发起新任务”可为每个 Task 单独选择模型、思考深度和 Fast 模式；选择会随 Task 保存在 SQLite，首轮和后续恢复同一 Codex 对话时都会显式传入。`default` 表示普通速度，不启用 Fast。

`PIPELINE_CODEX_TIMEOUT_MINUTES` 是单轮 Codex 的硬超时。超时会把 Turn 标记失败并将 Worker 留在 `attention`，不会自动恢复检查点；应按任务规模调整，但不建议设为无限。

`PIPELINE_GIT_AUTHOR_NAME` 和 `PIPELINE_GIT_AUTHOR_EMAIL` 会写入每个受管仓库的本地 Git 配置，用于 Relay 自动创建的交付提交，不依赖虚拟机登录用户的全局 Git identity。

`PIPELINE_CHECKPOINTS_ENABLED` 在检查点尚未准备好时保持 `false`。此时 Relay 仍会管理真实 VM、PowerShell Direct 和 Codex CLI，但不会恢复任何快照。完成并验证所有 `PROJECT_READY` 后再改为 `true` 并重启服务。

1. Windows Defender 防火墙仅允许公司可信子网访问 TCP 4317 和网页端口；
2. `PIPELINE_ALLOWED_ORIGINS` 精确列出实际网页 Origin，不使用 `*`；
3. 如需跨不可信网络访问，在反向代理上启用 HTTPS 和真正的身份认证；
4. 不把 4317 发布到公网。

局域网 HTTP 页面默认连接“当前网页主机名:4317”，并允许在“系统 → 控制服务连接”中修改 API 地址。Cloudflare Tunnel 等 HTTPS 页面固定使用当前域名的同源 `/relay-control/api`；该路径由 `server/web.mjs` 转发到本机 4317，既会自动忽略浏览器里曾保存的内网 HTTP 地址，也不会依赖单独的 Cloudflare `/api` 入口。API 地址和使用者名称保存在浏览器 `localStorage`；点击左下角的使用者名称可以随时切换，后续任务、消息和人工操作会记录新的名称。

## 6. 网页配置 Project 和 Worker

先配置 Project，再配置 Worker。保存后先使用“探测”，不要直接发真实任务。

### 6.1 Project

关键字段含义：

| 字段                  | 示例                                 | 说明                                                           |
| --------------------- | ------------------------------------ | -------------------------------------------------------------- |
| 项目名称              | `Unity Client`                       | 网页显示名                                                     |
| Git 仓库地址          | `git@github.company/game/client.git` | 子机 Git 可访问的 origin                                       |
| 默认分支              | `main`                               | 新 Task 的基线                                                 |
| 子机项目路径          | `D:\Work\unity-client`               | PowerShell Direct 内执行 Git 的本地路径                        |
| 宿主机 SMB 路径       | `\\172.30.240.11\Work\unity-client`  | Codex 访问的路径；若每台工位 IP 不同，以 Worker 的共享路径覆盖 |
| Unity 版本            | `2022.3.62f1`                        | 运维备注/兼容性检查                                            |
| Unity Skill / MCP URL | `http://{internalIp}:8090/mcp`       | 交给宿主机 Codex 的 Unity Skill MCP 端点                       |
| Unity Health URL      | `http://{internalIp}:8090/health`    | 宿主机用于探活的轻量 HTTP 端点，返回 2xx 即健康                |
| Unity Save URL        | `http://{internalIp}:8090/api/save`  | 调度器请求保存全部 Unity 资产的 HTTP 端点                      |
| 基线检查点            | `PROJECT_READY`                      | 项目默认检查点                                                 |

三个 URL 都支持 `{internalIp}`、`{corporateIp}`、`{workerName}`、`{vmName}` 占位符，运行时会按实际 Worker 替换，适合一个项目绑定多台工位。`Unity Skill / MCP URL`、`Unity Health URL` 和 `Unity Save URL` 必须分别指向各自协议端点；不要用 `/health` 代替 MCP，也不要把保存操作做成探活请求。

### 6.2 Worker

| 字段            | 示例                                             | 说明                                                   |
| --------------- | ------------------------------------------------ | ------------------------------------------------------ |
| 显示名称        | `lin-worker-01`                                  | 网页显示名                                             |
| Hyper-V VM 名称 | `lin-worker-01`                                  | 必须与 `Get-VM` 结果完全一致                           |
| 绑定项目        | `Unity Client`                                   | 当前调度模型中一个工位绑定一个项目；留空可作为通用工位 |
| 内部 IP         | `172.30.240.11`                                  | 运维显示和固定管理地址                                 |
| 公司 IP         | `10.100.3.x`                                     | 可选，仅用于显示/外部访问记录                          |
| SMB 共享路径    | `\\172.30.240.11\Work\unity-client`              | 该工位上具体项目路径                                   |
| 基线检查点      | `PROJECT_READY`                                  | 可覆盖项目默认值                                       |
| DPAPI 凭据路径  | `C:\ProgramData\Relay\secrets\lin-worker-01.xml` | 仅存路径，不存密码                                     |

启用工位后，探测结果应同时为：VM、Heartbeat、SMB、Unity、Skill 健康。调度器只会领取 `enabled + ready + 空闲 + 项目兼容` 的工位。

## 7. 一轮任务的实际流程

1. 用户创建 Task，第一条 Turn 入队；队列按优先级降序、创建时间升序处理。
2. 没有兼容空闲工位时保持 `queued`，不会抢占正在运行的任务。
3. 调度器原子领取 Turn 和 Worker。
4. 若检查点已启用则恢复 Worker 的 `PROJECT_READY`；否则只启动真实虚拟机并等待 PowerShell Direct 可用。
5. 子机内 `git fetch --prune`：
   - 第一次 Turn 从 `origin/<baseBranch>` 创建任务分支；
   - 后续 Turn 从 `origin/<taskBranch>` 恢复同一分支；
   - 子机本地工作区被重置到该远端来源，并清理未跟踪文件。
6. 等待 Unity 进程、Unity Skill 和宿主机 SMB 路径可用。
7. 宿主机 Codex 在 SMB 工作目录执行：首轮创建持久 thread，后续轮恢复同一 thread。
8. Codex 完成后，先通过 Unity Save URL 保存全部资产。
9. 子机内 `git add -A`、按需 commit、push 任务分支，并用 `git ls-remote` 验证远端 SHA 与本地 SHA 一致。
10. 只有持久交付成功后，Turn 才标记成功；启用检查点时恢复 `PROJECT_READY`，否则保留已交付现场并释放工位。
11. 用户在同一 Task 追加微调时，新 Turn 重复上述流程，并继续同一分支、同一 Codex thread。

同一个 Task 可以随时追加多个 Turn，但任何时刻只执行一个，避免并发修改同一分支。关闭 Task 后发送新消息会自动重新打开。若上一轮失败并保留现场，最早的下一轮会绑定原 Worker，先只读验证分支、工作区、Unity 和 Skill，再继续 Codex；不得在这条路径执行检查点还原、`git reset --hard` 或 `git clean`。

若创建任务时关闭“完成后自动释放”，交付成功后 Worker 会保持 `reserved`，方便人工查看 Unity 现场；确认后再从工位页执行“释放”。取消仍在队列中的 Turn 不影响 Task 历史；取消已经开始执行的 Turn 会停止执行并把 Worker 留在 `attention`，必须先检查可能尚未持久化的现场。

## 8. 安全边界

- 生产路径固定为 `hyperv`；设置其他适配器会拒绝启动。网页用户名只用于归属记录，不提供权限隔离。
- 后端只调用仓库内固定 PowerShell 脚本和枚举动作，不接受网页提交任意 PowerShell。
- 工位重启、强制关机、恢复检查点会改变外部状态。忙碌工位默认拒绝操作；只有明确接受丢失未持久化现场时才使用强制操作。
- DPAPI 文件、Git 凭据、SMB 凭据、Codex 登录四者分离；数据库只存 DPAPI 文件路径。
- `PIPELINE_DATA_DIR` 包含用户需求、附件、日志、分支和提交信息，应按内部源代码数据同等级保护。
- 上传附件有大小上限，但仍应只允许可信用户访问；不要上传生产密钥、个人隐私或未授权数据。
- Codex 的 `workspace-write` 权限范围是选中的 SMB 工作区；仍应让共享根路径精确指向项目，不要指向整块系统盘或宽泛目录。
- 不要给服务账户域管理员权限；按 VM、共享目录和防火墙端口做最小授权。
- 网页和 API 当前面向受控内网。跨网访问应通过企业 VPN/反向代理/HTTPS，而不是直接端口映射。

## 9. 检查点日常更新策略

建议“每日滚动刷新 + 定期干净重建”，而不是长期使用一个越来越旧的快照。

### 9.1 每日滚动刷新

在低峰期逐台工位进行，不要同时 drain 全部池：

1. 在网页禁用一台工位，确认其没有 `currentTurn`，状态不是 `busy/preparing`；
2. 保留现有 `PROJECT_READY`，先重命名为带日期的回退检查点，例如 `PROJECT_READY_PREV_20260722`；
3. 从旧基线启动，切回默认分支，`fetch` 后硬重置到 `origin/main`；
4. 更新项目依赖，但不要在日常刷新中随意升级 Unity 大版本、驱动或系统；
5. 打开 Unity，等待导入、编译、Domain Reload 和 Skill 完全就绪；
6. 确认 Git clean、SMB、Heartbeat、PowerShell Direct、Unity/Skill/保存端点均正常；
7. 创建新的 `PROJECT_READY`；
8. 重新启用工位，先跑 canary；通过后再处理下一台；
9. 至少保留上一版基线到所有工位 canary 通过，之后再受控删除旧检查点。

不要在活动 Turn、未推送更改或 `attention` 现场上更新基线。

### 9.2 定期干净重建

每周或每月（按项目变化速度）从已封存的母盘/自动安装清单重建差分子机，清理 Windows、Unity Library、Git 凭据和工具链漂移。母盘保持只读；不要把任务产生的差分链反向合并到母盘。若需要更新母盘，创建新的版本化母盘并滚动迁移工位，旧母盘保留到新池验收完成。

触发提前重建的信号包括：检查点恢复显著变慢、`.avhdx` 链过深、Unity Library 反复损坏、工位间结果不一致、系统/Unity 安全更新或项目 Unity 版本升级。

## 10. 真实 canary 验收

canary 使用专门测试仓库或允许删除的测试分支，绝不直接用 `main` 做第一轮。

### 10.1 启动前只读检查

```powershell
# 管理员、Hyper-V、Node、Codex
.\scripts\hyperv\Test-PipelineHost.ps1

# 对象名和检查点
Get-VM -Name 'lin-worker-01'
Get-VMSnapshot -VMName 'lin-worker-01' | Format-Table Name, CreationTime

# 集成服务
Get-VMIntegrationService -VMName 'lin-worker-01' |
  Format-Table Name, Enabled, PrimaryStatusDescription

# SMB
Test-Path '\\172.30.240.11\Work\unity-client'
```

随后在网页执行 Worker “探测”。五项健康检查必须全部通过。

### 10.2 最小真实任务

发起一个只修改独立文本文件或测试 Prefab 的 canary Task，要求 Codex：

1. 读取项目；
2. 通过 Unity Skill 查看一个测试资产；
3. 做一个容易核验的小改动；
4. 保存并给出验证摘要。

验收记录：

- Turn 经历 `prepare → codex → saving/delivery → delivered → released`；
- Task 保存了非空 `thread_id`；
- 远端出现 `codex/task-...` 分支；
- 网页 commit SHA 与 `git ls-remote origin refs/heads/<branch>` 一致；
- Unity 序列化改动在远端 commit 中；
- 工位最终回到 `ready` 且五项健康通过。

### 10.3 会话恢复验收

在同一 Task 中“追加一轮”，要求微调上一轮内容：

- 分支名保持不变；
- `thread_id` 保持不变；
- 新 Turn 序号递增；
- 可由另一台兼容工位执行；
- 新远端 SHA 包含上一轮提交且成功验证；
- Codex 能理解上一轮上下文。

最后在隔离的测试仓库验证一次远端不可达场景，确认不会恢复检查点，Worker 进入 `attention`，现场可供人工检查。不要为了测试而破坏生产远端权限。

## 11. 故障处理

### 11.1 Push 或远端 SHA 验证失败

预期行为：Turn 失败，Task 需要处理，Worker 进入 `attention`；调度器明确记录“workspace was preserved and was not reset”。这是保护现场，不是清理失败。

处理顺序：

1. 禁止对该工位执行“恢复/释放/强制关机”；
2. 查看网页事件中的失败 phase、错误代码和分支名；
3. 进入子机检查 `git status`、当前分支、远端权限和网络；
4. 若改动有效，人工完成 commit/push，并核对远端 SHA；
5. 记录人工处置。确认远端已持久化或明确决定放弃后，才在网页恢复/释放工位；
6. 若需要让 Relay 重新执行，先确保远端分支包含应保留内容，再点击 Task 重试。

强制恢复检查点会永久丢掉仅存在该差分盘/内存中的改动。

### 11.2 Worker `attention`

常见原因：准备、Codex、Unity 保存、Git 推送、释放过程失败，或后端在 Turn 运行中重启。后端启动时会把中断 Turn 标为 `interrupted`，并保留工位现场。

先判断现场是否包含未持久化更改：

- **有或不确定**：保持 attention，人工检查子机和日志；
- **确认无需要保留内容**：执行“恢复”回到 `PROJECT_READY`，再“探测”；
- **VM 无响应**：先普通重启；只有普通关闭失败且已接受数据丢失时才“强制关机”。

不要仅为了让仪表盘变绿就直接释放 attention 工位。

### 11.3 Unity 或 Skill 不健康

- `unity=false`：确认自动登录成功、Unity 启动项/计划任务存在、项目路径正确、许可证有效、没有阻塞对话框。
- `skill=false`：在子机和宿主机分别访问配置 URL；检查监听地址、端口、防火墙和 Unity Console。
- Unity 界面被弹窗卡住：在子机检查 `C:\\ProgramData\\Relay\\UnityDialogGuard\\logs`。未知窗口会进入 `unknown-dialogs.jsonl`；人工点击一次目标按钮后应写入 `learned-rules.json`，以后同类窗口会自动处理。
- `unitySaveUrl` 失败：保留工位，先人工保存并确认资产落盘；不要启用全局跳过作为长期修复。
- 新检查点才出现故障：回滚到上一版基线，修复后重新制作检查点。

### 11.4 SMB 不健康

用运行 Relay 的账户执行 `Test-Path`，检查共享名、NTFS/共享权限、Windows 凭据管理器、内部网卡和防火墙“文件和打印机共享”。不要把 Worker 的 `sharePath` 填成仅在子机内部有效的 `D:\...`。

### 11.5 Codex 未登录或会话无法恢复

以服务账户检查：

```powershell
$env:CODEX_HOME = 'C:\ProgramData\Relay\codex-home'
codex --version
codex login
```

确认服务实际继承相同 `CODEX_HOME`。若 SQLite 有 `thread_id` 但 `CODEX_HOME` 丢失，不要伪造新 ID；保留原 Task/分支作为审计记录，可在人工确认后新建 Task 继续。

### 11.6 API 无法从其他电脑访问

按顺序检查：

1. `/api/health` 在宿主机本地是否可访问；
2. `PIPELINE_HOST` 是否为 `0.0.0.0`；
3. Windows 防火墙是否只向正确公司子网开放 4317；
4. 网页“系统”页 API 地址是否为宿主机公司 IP；
5. `PIPELINE_ALLOWED_ORIGINS` 是否包含完整的协议、主机和网页端口；
6. 浏览器开发者工具中写操作是否带有 `X-Pipeline-User`（只用于用户名归属；读取快照不会携带）；
7. HTTPS 网页不能直接请求 HTTP API，生产环境应由反向代理统一 HTTPS。

## 12. Windows 服务部署建议

不要直接把开发用 `npm run dev` 当生产服务。推荐把网页和控制 API 分成两个 Windows 服务，并使用同一专用服务账户：

- **RelayControl**：`node --env-file=C:\ProgramData\Relay\relay.env <项目根>\server\index.mjs`
- **RelayWeb**：先执行 `npm run build`，再以 `npm run start:web` 启动；固定监听公司内网地址或仅监听反向代理回环地址。
- 手工更新网页后，可运行 `powershell -ExecutionPolicy Bypass -File .\scripts\Restart-RelayWeb.ps1`。脚本会核验 3000 端口确实属于 Relay，停止误用的开发服务器或旧生产进程，并以隐藏窗口启动生产构建。

可使用 WinSW、NSSM 或企业现有 Windows 服务封装器。无论选择哪种工具，都应配置：

- “登录身份”为创建 DPAPI 文件和 Codex 登录的同一账户；
- 加载该服务账户的用户配置文件，使 Codex/Git 凭据存储可见；
- 工作目录为项目根；
- 自动启动采用“延迟启动”，网络不可用时指数退避重试；
- 标准输出和错误输出写入受控日志目录并轮转；
- 恢复策略只对**启动失败**重启服务。运行中意外退出后，Relay 会把活动 Turn 标为中断并保留现场，运维人员必须检查 attention 工位；
- 依赖项包含 Hyper-V 管理服务和网络；
- 更新前先在网页暂停调度，等待活动 Turn 结束，再停止服务并备份数据。

建议的升级顺序：

1. 暂停调度器；
2. 等待 `activeTurns=0`，确认没有 busy/preparing 工位；
3. 停止 Web 和 Control 服务；
4. 备份 `PIPELINE_DATA_DIR` 与 `CODEX_HOME`；
5. 更新代码，执行 `npm install`、`npm test`、`npm run build`；
6. 先以隔离的测试数据目录启动真实控制服务；
7. 启动真实 Control，再启动 Web；
8. 运行 Worker 探测和最小 canary；
9. 恢复调度。

## 13. 备份、日志与日常巡检

持久目录默认包含：

```text
PIPELINE_DATA_DIR\pipeline.sqlite
PIPELINE_DATA_DIR\uploads\
PIPELINE_DATA_DIR\logs\<task-id>\<turn>.jsonl
PIPELINE_DATA_DIR\logs\<task-id>\<turn>.final.json
```

日常至少检查：

- ready 工位数量和五项健康状态；
- 队列中等待时间异常的 Turn；
- attention / interrupted / release-failed 事件；
- 数据盘、检查点盘、上传和日志目录剩余空间；
- 远端任务分支增长和保留策略；
- `PROJECT_READY` 最近更新时间与 canary 结果；
- Codex 登录和 Git/Unity 许可证有效期。

日志、附件和任务分支的清理应有明确保留期，并先确认不再用于审计或后续微调。当前系统不会自动删除远程任务分支，也不会自动丢弃 attention 现场。
